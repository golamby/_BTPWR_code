# BTPWR：签名等级、单轮招募、请求者授权恢复

当前默认机制见 `DECISIONS.md`。这里是新的角色分离实现，旧 `Code_Reproduction` 的进度规划实验属于历史数值研究，不能当成这里的私有流水线。

流程：注册 → 服务器校验当前签名等级并单轮招募 → 锁定名单与预算 → 实测报告加密给请求者 → 解密入选信誉和实测 → OTHER-C参考 → 可信实测锚点恢复 → 半权重次级参考和封顶多区域评分 → 全员密文重随机化及令牌换新 → 结算新根。

请求者不在招募前解密全体信誉。签名接口仅接受令牌摘要、域、任务、轮次、序列号和等级；完整密文令牌留在服务器/工人，验签时检查完整令牌摘要。预锁定接口不接收任何信誉密文，锁定后只发送入选者密文。未入选信誉原值携带。只有当服务器收到每个入选者的完整加密后继和新等级时，才允许换新；不能静默保留一个漏发更新的旧状态。

## 权限与实现

- 服务器可见匿名稳定所有者、路由及粗等级，不持有精确信誉/报告解密密钥。
- 请求者招募锁定后可见入选者的精确信誉、实测和区域，不得到稳定所有者路由表。
- 注册机构保留真实身份关系。三者非串通。
- 每轮新别名、全员令牌换新；精确数值与轨迹仍可能形成统计指纹。
- Ed25519、X25519/HKDF-SHA256/AES-GCM、mTLS、2048位Paillier；链上是实际Solidity/PyEVM执行。
- 合约核验授权、上下文、预算、状态根和防重放。评分正确性依赖按协议工作的请求者。现有合约记录支付承诺，不实际兑付货币。
- 当前原型按配置生成80个默认客户状态，保留100客户规模检查；使用8个并发客户线程、同机分进程TLS服务。它不是100部物理手机或广域共识链；成功路径要求在线测试队列完成阶段。

## 入口

`prepare.py` 生成私有测试凭证与世界；`launch_roles.py` 启动3个在线服务；`run_clients.py` 驱动客户流程；`stop_roles.py` 只停止经路径和命令核对的对应服务。

`anonymous_state.py` 负责等级、Paillier密文、批量换新和当前状态准入；`services.py` 连接招募、评分和结算；`RequesterRound.sol` 与 `evm_ledger.py` 执行链上状态机；`securewire.py`、`transport.py` 提供真实加密传输。`reconstruct_original_architecture.py` 在原版SVG上重构图，保留地图和实体图标。数值反馈复用 `Code_Reproduction/src/count_feedback.py`。

当前服务默认配置为80工人、50轮、每轮450；prepare.py同时支持50–100工人和显式预算。敏感性实验的适配器必须遵守实验方案和相同权限边界。不能仅改结果标签，或将旧的精确信誉/实际足迹模型输出当成新协议结果。

## 独立工人认证与请求者任务绑定修正

当前规范实现采用每工人独立的mTLS证书和私钥，TLS证书名称绑定完整匿名所有者路由。工人外层RPC再由自己的Ed25519所有者密钥签名；服务器的工人验签映射仅保存在服务器登记表，不放入请求者可见的公共配置。工人只可调用claim/offer/report，且请求中的路由与报告别名必须归属于该认证工人。调度端只负责注册/启动、选取/完成及测量，不能用其调度证书代替工人调用。

请求者从自己的固定任务计划签署每轮任务标识、轮次、虚拟任务多重集、预算及策略摘要；调度端只能按轮次领取证书，不能提交任意任务集合让它盲签。选取前验签及核对上下文；打开轮次时，请求者再次对照自己的计划，并将任务证书摘要与报价摘要共同绑定到原有offers根。Solidity接口不变，不增加数值计算证明。

17项状态/传输/签发/认证及任务绑定检查通过，另有两轮80工人的新认证功能路径逐轮匹配明文参考。数值策略、隐私授权和参与实体均未改变。旧6组50轮与9次网络测量属于共享测试驱动TLS修订，已经独立归档；新认证版本的性能必须在服务器空闲后重新测量，不能直接沿用旧耗时和通信量。

测试驱动仍在同一主机保存合成世界与所有客户测试凭证，并以8线程驱动80/100套独立密钥和状态；这是受信测试调度器与审计端，不是100台物理设备或对恶意测试调度器的安全证明。请求者只持有自己的任务计划，无模拟真值、工人类型或未来工人报告。
